# Authentication & Roles Service --- API Documentation

## 1. Overview

The Authentication & Roles Service manages user registration, login,
access-token validation, and role information for the Photography Studio
Booking system.

It has its own Laravel application and database (`auth_db`). Other
microservices should communicate with this service through its REST API.
They should **not connect directly to `auth_db`**.

### Current development environment

  Setting          Value
  ---------------- ----------------------------------------
  Framework        Laravel 13.42.0
  Authentication   Laravel Sanctum personal access tokens
  Local base URL   `http://127.0.0.1:8000`
  Database         `auth_db`

> **Important:** `127.0.0.1` is only accessible from the same computer.
> Before teammates on other computers can call this service, the team
> must agree on a reachable development URL (for example, a shared LAN
> address or deployed development server) and configure it through an
> environment variable in each service.

## 2. User roles

The service currently uses these role values:

  Role value       Description
  ---------------- ---------------
  `admin`          Administrator
  `photographer`   Photographer
  `client`         Client

Public registration always assigns the `client` role. The registration
request must not be used to assign an elevated role.

## 3. API endpoints

All endpoints use the `/api` prefix.

  -----------------------------------------------------------------------
  Method            Endpoint          Authentication    Purpose
  ----------------- ----------------- ----------------- -----------------
  `POST`            `/api/register`   Not required      Register a new
                                                        client account

  `POST`            `/api/login`      Not required      Verify
                                                        credentials and
                                                        issue a Sanctum
                                                        token

  `GET`             `/api/user`       Bearer token      Validate the
                                      required          token and return
                                                        the authenticated
                                                        user's identity
  -----------------------------------------------------------------------

### 3.1 Register

**Request**

`POST /api/register`

Header:

``` http
Accept: application/json
Content-Type: application/json
```

JSON body:

``` json
{
  "name": "Test Client",
  "email": "client@example.com",
  "password": "Client@12345",
  "password_confirmation": "Client@12345"
}
```

The service validates the fields, requires a unique email address,
hashes the password, and assigns the new account the `client` role. The
caller cannot choose the role through public registration.

**Successful response --- HTTP 201**

``` json
{
  "message": "Registration successful.",
  "user": {
    "id": 5,
    "name": "Test Client",
    "email": "client@example.com",
    "role": "client",
    "is_active": true
  }
}
```

The `id` above is an example; the actual value is generated by the
database.

**Validation failure --- HTTP 422**

Laravel returns a JSON validation response. For example, a duplicate
email or mismatched password confirmation will produce a validation
error.

### 3.2 Login

**Request**

`POST /api/login`

Header:

``` http
Accept: application/json
Content-Type: application/json
```

JSON body:

``` json
{
  "email": "client@example.com",
  "password": "Client@12345"
}
```

The service validates the credentials and checks that the account is
active. If successful, it creates a Sanctum personal access token.

**Successful response --- HTTP 200**

``` json
{
  "message": "Login successful.",
  "user": {
    "id": 5,
    "name": "Test Client",
    "email": "client@example.com",
    "role": "client"
  },
  "token": "RETURNED_SANCTUM_TOKEN"
}
```

Save the returned token securely. Do not commit real tokens to source
control or share them in messages.

**Possible error responses**

  HTTP status                  Meaning
  ---------------------------- --------------------------------
  `401 Unauthorized`           Email or password is incorrect
  `403 Forbidden`              Account is inactive
  `422 Unprocessable Entity`   Request validation failed

### 3.3 Get the authenticated user

**Request**

`GET /api/user`

Headers:

``` http
Accept: application/json
Authorization: Bearer RETURNED_SANCTUM_TOKEN
```

This endpoint is protected by `auth:sanctum`. It validates the supplied
token and returns the identity associated with it.

**Successful response --- HTTP 200**

``` json
{
  "id": 5,
  "name": "Test Client",
  "email": "client@example.com",
  "role": "client",
  "is_active": true
}
```

**Unauthenticated response --- HTTP 401**

A missing or invalid token should be rejected.

## 4. Calling the service from another microservice

The consuming service should:

1.  Receive the access token from the client after login.
2.  Send the token to the Authentication Service's `GET /api/user`
    endpoint.
3.  Check the HTTP response.
4.  If the response is `200`, use the returned user ID and role for its
    own business logic.
5.  If the response is `401`, treat the request as unauthenticated.

Example JavaScript request:

``` javascript
const response = await fetch(`${AUTH_SERVICE_URL}/api/user`, {
    method: 'GET',
    headers: {
        'Accept': 'application/json',
        'Authorization': `Bearer ${accessToken}`
    }
});

if (!response.ok) {
    // Reject the request if the token is invalid or the user is unauthenticated.
    throw new Error(`Authentication failed: ${response.status}`);
}

const user = await response.json();

// Example fields: user.id, user.name, user.email, user.role
```

Configure `AUTH_SERVICE_URL` for each environment. Do not hardcode
`127.0.0.1` in code that teammates will run on different computers.

### Example environment configuration

``` env
AUTH_SERVICE_URL=http://127.0.0.1:8000
```

Each teammate should use the actual reachable URL for their environment.

> **Architecture note:** A Sanctum token is validated by the
> Authentication Service that issued it. Other microservices should call
> this service to validate the token; they should not assume their own
> local Sanctum installation can validate tokens from a separate
> database.

## 5. Role-based access control

The Authentication Service has a `RoleMiddleware` that can restrict
Laravel routes to one or more roles. It is registered with the `role`
alias in `bootstrap/app.php`.

Examples:

``` php
// Admin only
Route::middleware(['auth:sanctum', 'role:admin'])->group(function () {
    // Admin-only routes
});

// Admin or Photographer
Route::middleware(['auth:sanctum', 'role:admin,photographer'])->group(function () {
    // Staff routes
});
```

The middleware returns:

-   `401` when there is no authenticated user.
-   `403` when the authenticated user's role is not in the allowed
    roles.

The consuming microservices must still enforce their own business
permissions. Receiving a user's role is not a substitute for checking
whether that role may perform a particular operation.

## 6. Current implementation status and limitations

Implemented and tested during development:

-   Public client registration.
-   Registration validation, including duplicate-email and
    password-confirmation checks.
-   Server-side assignment of the `client` role during public
    registration.
-   Login with credential validation.
-   Inactive-account login restriction.
-   Sanctum token generation.
-   Protected `GET /api/user` endpoint.
-   Rejection of missing and invalid tokens.
-   Role middleware supporting one or multiple allowed roles.

Not yet documented as available API functionality:

-   Logout endpoint and token revocation.
-   Admin API for creating Photographer accounts or changing user roles.
-   Admin API for activating and deactivating accounts.
-   Production/deployed base URL and cross-computer integration testing.

Do not build integrations that depend on these unfinished endpoints
until they have been implemented and tested.

## 7. Development notes

-   Keep `.env` files and database credentials private. Do not commit
    secrets.
-   Do not share real access tokens.
-   Use test accounts for integration testing.
-   The local development server must be running for other applications
    to call the service.
-   Before cross-computer testing, make sure the service is reachable
    from the teammate's machine and that firewall/network settings
    permit the connection.
